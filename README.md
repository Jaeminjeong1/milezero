# milezero
물류 AI 해커톤 MoveAI 카카오모빌리티 부문

## 백엔드 우선 구현

현재 브랜치의 구현 범위는 프런트엔드를 제외한 다음 파이프라인이다.

`GPS 집계 특징 → 배송 마찰 탐지 → 중립 질문 → 텍스트·음성·사진 분석 → 개인정보 제거 → 후보 지식 검증·저장 → 다음 기사 안내 → 사실·도움 피드백`

### 실행

Node.js 22와 pnpm을 사용한다.

```bash
pnpm install
cp .env.example .env
pnpm dev
```

필수 서버 환경변수:

- `GEMINI_API_KEY`
- `GEMINI_MODEL`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `PORT` — 생략하면 `3000`

Supabase 프로젝트에는 먼저 `supabase/migrations/202608130001_milezero_pipeline.sql`을 적용한다. 공개 클라이언트는 DB에 직접 접근하지 않으며 서버의 service role만 제한된 RPC를 호출한다.

### API

- `POST /v1/questions`: 브라우저에서 계산한 GPS 집계 특징으로 질문 생성
- `POST /v1/reports`: 기사 응답 분석, 개인정보 제거, 후보 지식 및 기본 포인트 저장
- `GET /v1/knowledge`: 검증된 가이드와 별도의 후보 확인 요청 조회
- `POST /v1/feedback`: `CONFIRM`, `CONTRADICT`, `HELPFUL` 피드백 반영
- `GET /health`: 배포 상태 확인
- `GET /ready`: Supabase RPC 연결을 포함한 요청 처리 준비 상태 확인

데모 단계에서는 기사 가명 ID를 `x-driver-id` 헤더로 전달한다. 외부 파일럿 전에는 이 헤더를 신뢰하지 않고 인증 토큰의 사용자 ID로 서버에서 교체해야 한다.

### 개인정보 경계

- 원본 GPS 좌표는 백엔드 API가 받지 않는다.
- 원본 음성·사진은 요청 메모리에서 Gemini 분석에만 사용하며 저장하지 않는다.
- 텍스트는 Gemini 호출 전과 구조화 결과 저장 전에 모두 마스킹한다.
- 데이터베이스에는 비식별 요약·원자 주장·검증 근거·포인트만 저장한다.
- 개인정보 발견 시 재질문하지 않고 해당 부분만 제거한다.

### 검증

```bash
pnpm test
pnpm typecheck
pnpm build
pnpm qa:demo
```

`qa:demo`는 외부 API 키 없이 합성 데이터만 사용해 `마찰 질문 → 제보 → 독립 기사 확인 → 검증 가이드 → 도움 피드백 → 추가 포인트`를 HTTP API 수준에서 한 바퀴 실행한다. 운영 서버의 Gemini·Supabase 구성과는 분리된 QA fixture다.

### Railway 배포

루트 `Dockerfile`과 `railway.json`을 사용한다. Railway 서비스에 네 가지 필수 환경변수를 secret으로 등록한 뒤 배포한다.

```bash
railway up
railway logs
railway domain
```

# 1. 문제 정의

배달·퀵 운송인은 내비게이션과 GPS를 통해 **배송지 주소 근처까지는 비교적 정확하게 이동할 수 있다.**

하지만 배송은 주소에 도착했다고 끝나지 않는다.

* 실제 차량 출입구가 어디인지
* 어느 위치에 정차·하역해야 하는지
* 차량 높이·종류에 따른 진입 제한이 있는지
* 경비실 등록이나 방문 절차가 필요한지
* 어느 엘리베이터를 이용해야 하는지
* 건물 내부에서 수령지까지 어떻게 이동해야 하는지

와 같은 정보는 일반적인 지도나 GPS만으로 파악하기 어렵다.

운송인은 결국 현장에서 직접 탐색하거나 수령인에게 연락하며 문제를 해결한다. 하지만 이렇게 얻은 경험은 대부분 해당 운송인의 기억에만 남고, 다음 운송인은 같은 장소에서 다시 같은 시행착오를 겪는다.

University of Washington Urban Freight Lab의 **Final 50 Feet 연구** 역시 주차·하역 이후 건물 진입, 엘리베이터, 보안 절차, 최종 인계까지를 도시 배송의 별도 구간으로 분석한다.

Seattle Municipal Tower 사례에서는 평균 배송시간 약 20분 가운데 12.2분이 화물 엘리베이터 이동과 층별 전달 과정에 사용됐다.

카카오 T 퀵 역시 배송지 도착 후 대기나 엘리베이터 부재 등 일부 현장 조건을 추가 비용 기준으로 두고 있다.

즉, **배송지 도착 이후의 환경은 실제 배송시간과 비용을 결정하는 중요한 변수**다.

> 여기서 Last 50 Feet는 문자 그대로 마지막 15m를 의미하기보다는, 차량이 배송지에 도착한 이후 실제 인계가 완료되기까지의 마지막 배송 구간을 의미한다.

## 우리가 해결하려는 문제

GPS는 주로 다음 사실을 알려준다.

**“운송인이 어디로 이동했는가.”**

하지만 배송 효율을 높이려면 그 행동의 맥락까지 알아야 한다.

* 왜 이 출입구를 선택했는가
* 왜 해당 위치에 정차했는가
* 왜 특정 차량은 진입하지 못했는가
* 왜 같은 장소를 반복 이동했는가
* 어떤 출입 절차가 필요했는가
* 어디에서 시간이 지연됐는가
* 다음 운송인은 어떻게 행동하면 되는가

MileZero는 운송인이 현장에서 습득한 이러한 **배송 현장 암묵지**를 수집하고 구조화하여 다음 배송에서 재사용 가능한 **현장 운영 지식**으로 만드는 것을 목표로 한다.

※ 50m / 75m / 100m는 Last 50 Feet의 정의가 아니다.
배송지 접근을 감지하고 현장 마찰 분석을 시작하기 위한 **지오펜스 실험 범위**로 사용한다.

# 2. 아이템 개요

**MileZero는 배송지 도착 이후 발생하는 운송인의 현장 경험을 데이터화하는 ‘Last 50 Feet 현장 지식 플랫폼’이다.**

기존 GPS·운행 로그를 통해 배송지 근방에서 발생한 **행동 결과**를 파악하고,

GPS만으로 알 수 없는 행동의 **이유와 해결 방법**을 운송인의 최소한의 피드백을 통해 보완한다.

## 운행 로그에서 자동으로 얻는 데이터

* 배송지 접근 경로
* 실제 차량 진입 방향
* 정차 위치
* 체류시간
* 반복 이동
* 경로 이탈
* 정차 횟수
* 배송 완료 처리 위치
* 배송지 반경 진입부터 완료까지의 시간

## 운송인에게 확인해야 하는 현장 지식

* 실제 사용 가능한 차량 출입구
* 해당 출입구를 선택해야 하는 조건
* 권장 정차·하역 위치
* 차량 높이·종류별 진입 제한
* 경비실·방문 등록 절차
* 화물 엘리베이터 위치와 이용 방법
* 건물 내부 이동 방법
* 현장에서 발생한 지연 원인
* 문제가 발생했을 때의 대체 행동

즉,

**GPS = 무엇이 일어났는가**

**운송인 경험 = 왜 그렇게 행동했는가**

를 결합한다.

AI는 이를 다음과 같은 구조의 **배송 현장 운영 지식**으로 변환한다.

`장소 / 적용 조건 / 현장 마찰 / 권장 행동 / 근거 / 최근 확인일 / 신뢰도`

예:

> 서울 OO타워 / 1톤 차량 / 지하주차장 높이 제한 / 후문 진입 후 B2 하역장 이용 / 기사 14명 확인 / 3일 전 확인 / 신뢰도 높음

축적된 데이터는 우선 다음 운송인의 배송을 지원하고, 장기적으로는 자율주행 배송차량이나 배송로봇이 목적지에서 행동을 결정할 때 활용할 수 있는 **Last-50-Feet 운영 지식 계층**으로 확장한다.

이는 자율주행 모델 자체를 학습시키는 카메라·LiDAR 센서 데이터와는 다르다.

대신 다음과 같은 운영 판단을 지원한다.

* 어느 출입구를 선택해야 하는가
* 차량이 어디까지 진입할 수 있는가
* 어디에 정차·하역해야 하는가
* 어떤 출입 절차가 필요한가
* 어느 지점부터 사람이 직접 이동해야 하는가

# 3. 주요 기능

## 기능 1. 배송지 현장 마찰 신호 자동 탐지

기존의 ‘이상 행동’이라는 표현보다는 **배송 마찰(Friction)**이라는 개념을 사용한다.

배송지 지오펜스 진입 이후 GPS와 업무 로그를 분석한다.

다음과 같은 패턴이 나타나면 배송 과정에서 현장 마찰이 발생했다고 판단한다.

* 동일 구간 반복 이동
* 배송지 인근 장시간 체류
* 짧은 간격의 반복 정차
* 일반적인 접근 경로에서 이탈
* 등록된 배송지와 실제 배송 완료 위치 차이
* 동일 배송지 대비 비정상적으로 긴 완료시간

모든 배송에서 운송인에게 질문하지 않고, **정보 가치가 높은 배송만 자동으로 선별**한다.

# 4. 운송인에게 정보를 쉽게 얻는 방법

MileZero의 핵심은 운송인에게 별도의 ‘정보 등록 업무’를 요구하지 않는 것이다.

운송인이 직접 긴 글을 작성하게 하면 참여율이 낮아질 가능성이 높다.

따라서 수집 방식을 다음 3단계로 설계한다.

## 1단계. 행동 데이터는 자동 수집

운송인에게 묻지 않아도 알 수 있는 정보는 GPS와 업무 로그에서 먼저 얻는다.

예를 들어,

> 배송지 반경에 들어온 뒤 건물 주변을 두 번 이동하고 후문에 정차했다.

라는 사실은 GPS로 알 수 있다.

운송인에게 다시

> “어디로 이동했나요?”

라고 묻지 않는다.

대신 GPS가 알 수 없는 것만 질문한다.

> “후문을 이용한 이유가 무엇인가요?”

---

## 2단계. 배송 완료 후 1~2회 터치로 확인

배송 중에는 운송인을 방해하지 않는다.

배송 완료 직후 필요한 경우에만 짧은 질문을 노출한다.

예:

**이곳에서 시간이 오래 걸린 이유가 무엇인가요?**

* 출입구 찾기
* 정차·하역
* 차량 진입 제한
* 출입 등록
* 엘리베이터
* 건물 내부 이동
* 수령인 연락
* 기타

대부분의 제보는 여기서 종료한다.

추가적인 설명이 필요한 경우에만

* 음성
* 짧은 텍스트
* 사진

입력을 선택적으로 제공한다.

---

## 3단계. ‘제보’보다 ‘확인’을 요청

새로운 정보를 매번 입력받기보다 기존 정보를 다음 운송인에게 확인받는다.

예:

> 이전 운송인은
> **“1톤 차량은 정문 지하주차장 진입이 어렵다”**고 알려줬습니다.

**현재도 맞나요?**

`맞아요` / `달라졌어요`

또는

> **B2 하역장을 이용하셨나요?**

`네` / `아니요`

이를 통해 운송인은 새로운 글을 작성하지 않고도 **한 번의 터치로 데이터를 검증**할 수 있다.

---

# 5. 입력 부담을 더 줄이는 수집 장치

## 음성 메모

운전 중이나 배송 중 입력하는 것이 아니라 배송 완료 후,

> “이 장소에서 다음 기사에게 알려주고 싶은 게 있나요?”

라는 선택적 질문을 제공한다.

운송인은 짧게 말한다.

> “정문 말고 후문으로 들어가야 돼요. 정문은 1톤차 못 들어가요.”

AI가 이를 자동 구조화한다.

---

## 현장 태그

자주 발생하는 정보를 태그 형태로 제공한다.

예:

* #후문진입
* #지하진입불가
* #경비실등록
* #화물엘리베이터
* #하역장있음
* #도로정차필요
* #수령인연락필요

운송인은 긴 설명 대신 필요한 태그만 선택할 수 있다.

---

## 사진 기반 입력

출입구·하역장·안내 표지판처럼 텍스트보다 사진이 빠른 경우 사진을 활용한다.

예:

* 화물차 출입구
* 하역장 위치
* 화물 엘리베이터 안내판
* 차량 높이 제한 표지
* 방문 차량 등록 안내

AI가 사진에서 장소 운영 정보를 추출한다.

단, 얼굴·차량번호·연락처·공동현관 비밀번호 등 불필요한 개인정보는 저장 대상에서 제외한다.

---

# 6. AI 기반 현장 지식 구조화

운송인 입력:

> “1톤차는 정문 지하로 못 들어가요. 동문으로 들어가서 105동 뒤에 세우고 경비실에서 업체명 말하면 됩니다.”

AI 구조화:

* 장소: 해당 단지
* 적용 차량: 1톤 차량
* 현장 마찰: 정문 지하 진입 제한
* 권장 출입구: 동문
* 권장 정차 위치: 105동 후면
* 필요 절차: 경비실 방문
* 확인 정보: 업체명 전달

중요한 것은 AI가 **새로운 사실을 만들어내지 않는 것**이다.

운송인이 언급하지 않은

* 소요시간
* 운영시간
* 차량 높이
* 정확한 위치

등은 임의로 생성하지 않는다.

예상 추가 소요시간과 같은 값은 한 명의 자연어 제보에서 생성하지 않고, 충분한 운행 로그가 축적된 이후 실제 데이터를 기반으로 계산한다.

---

# 7. 데이터 검증 및 최신성 관리

한 명의 제보를 즉시 사실로 확정하지 않는다.

다음 데이터를 조합해 장소별 정보의 신뢰도를 계산한다.

* GPS 이동 패턴과 제보 내용의 일치 여부
* 동일 내용을 확인한 운송인 수
* 실제 해당 행동을 수행한 운송인 비율
* 도움됐어요
* 정보가 달라졌어요
* 최근 확인 날짜
* 차량 종류
* 시간대
* 필요 시 관리주체 확인

예:

> 1톤 차량 지하 진입 불가
> 최근 30일 18명 확인 / 반대 1명
> 마지막 확인 2일 전

오래 확인되지 않은 정보는 신뢰도를 낮추거나 재확인을 요청한다.

---

# 8. 운송인 참여 유도

단순히 제보 개수에 보상을 지급하면 저품질 데이터가 늘어날 수 있다.

따라서 **제보 자체가 아니라 실제 도움이 된 정보에 보상**한다.

예:

* 다른 운송인이 `도움됐어요`를 누름
* GPS 로그를 통해 실제 동일 경로가 반복 확인됨
* 여러 운송인이 같은 정보를 확인함
* 장기간 정확한 정보를 제공함

이러한 경우에만 기여도를 높인다.

기여도가 높은 운송인에게는

* AI 트레이너 배지
* 현장 전문가 배지
* 포인트
* 추가 인센티브

등을 제공할 수 있다.

이를 통해

**운송인 → 데이터를 제공하는 사람**

이 아니라

**운송인 → 자신의 경험으로 다음 운송인을 돕는 현장 전문가**

라는 참여 구조를 만든다.

---

# 9. 다음 운송인에게 제공하는 현장 가이드

같은 배송지에 접근하는 다음 운송인에게 모든 데이터를 보여주지 않는다.

배송 전에 **지금 필요한 행동 정보만 제공**한다.

### OO타워 배송 가이드

* 후문 화물차 출입구 이용
* 1톤 차량 지하 진입 제한
* B2 하역구역 이용
* 경비실 방문 등록 필요
* 화물 엘리베이터 B2 연결

신뢰도 높은 정보만 우선 노출한다.

운송인은 배송이 끝난 뒤

> 이 정보가 도움이 됐나요?

`도움됐어요` / `정보가 달라요`

만 선택하면 된다.

이 피드백은 다시 데이터 검증에 사용된다.

---

# 10. 모델 및 프롬프트

## AI 역할

멀티모달 LLM을 이용해 운송인의 음성·텍스트·사진을 **배송지에서 반복적으로 활용 가능한 현장 운영 지식**으로 변환한다.

## 입력

* 배송지 좌표
* GPS 이동 이력
* 차량 종류
* 배송 시간대
* 배송 완료 시각
* 배송 마찰 신호
* 선택형 응답
* 음성·텍스트
* 현장 사진
* 기존 장소 정보

## 출력

* 실제 출입구
* 정차·하역 위치
* 차량 제약조건
* 출입 절차
* 내부 이동 정보
* 배송 마찰 원인
* 권장 행동
* 대체 행동
* 적용 조건

## 프롬프트 핵심

> 운송인의 현장 경험에서 동일 장소의 다음 배송에도 재사용할 수 있는 정보만 추출한다.
> 장소 / 적용 조건 / 현장 마찰 / 권장 행동 / 대체 행동으로 구조화한다.
> 입력에 명시되지 않은 내용은 추측하지 않는다.
> 일회성 고객 정보, 개인 연락처, 비밀번호 등 개인정보·민감정보는 저장 대상에서 제외한다.

# 11. 더미데이터 설계

실제 카카오모빌리티 운행 데이터를 사용할 수 없으므로 데모에서는 합성 데이터를 사용한다.

핵심은 임의로 만든 값을 실제 배송 통계처럼 제시하지 않는 것이다.

## 데이터 설계 기준

### 1. 실제 연구에서 확인된 현장 요소를 변수로 사용

* 차량 정차·하역
* 건물 진입
* 보안·출입 절차
* 엘리베이터
* 건물 내부 이동
* 최종 인계

Urban Freight Lab의 Final 50 Feet 연구에서 다루어진 현장 요소를 데이터 모델 설계의 참고 기준으로 사용한다.

### 2. 실제 사례 수치는 범위 참고용으로만 사용

Seattle Municipal Tower의 약 20분 / 내부 이동 12.2분 사례는 복잡한 고층 오피스 배송 사례다.

이를 한국 퀵·배달의 평균값으로 사용하지 않는다.

다만,

> 건물 도착 이후에도 수분에서 수십 분 규모의 현장 시간이 발생할 수 있다.

는 문제 설정의 근거로 사용한다.

### 3. 배송지 난이도별 시나리오 구성

**단순**

* 차량 진입 가능
* 즉시 정차
* 별도 출입 절차 없음

**보통**

* 특정 출입구 이용
* 경비실 등록 또는 엘리베이터 탐색 필요

**복잡**

* 차량 진입 제한
* 별도 하역장 이용
* 방문 등록
* 화물 엘리베이터
* 장거리 내부 이동

각 시간 값은 실제 통계가 아니라 **시뮬레이션 가정값**임을 명확히 표시한다.

### 4. 지오펜스 범위 실험

* 50m
* 75m
* 100m

각 범위에서 배송 마찰 신호를 얼마나 정확하게 포착할 수 있는지 비교한다.

# 12. 더미데이터 핵심 구조

배송 완료 과정은 다음과 같이 분해한다.

`배송지 근방 진입 → 차량 출입구 탐색 → 정차·하역 → 출입 절차 → 건물 내부 이동 → 최종 인계`

예시 데이터:

* geofence_entered_at
* delivered_at
* entrance_search_time
* parking_search_time
* access_process_time
* internal_move_time
* handoff_time
* route_deviation_count
* stop_count
* vehicle_type
* building_type
* access_restriction
* driver_feedback
* guide_provided
* guide_helpful

이를 이용해 동일한 배송 조건에서

* 현장 지식이 없는 운송인
* MileZero 가이드를 받은 운송인

의 행동 차이를 비교한다.

# 13. 핵심 검증 지표

## 1순위 KPI

**배송지 지오펜스 진입 → 최종 배송 완료까지 소요된 시간**

MileZero가 줄이려는 것은 전체 운행시간이 아니라 배송지에 도착한 이후 발생하는 탐색과 시행착오이기 때문에 가장 직접적인 성과 지표다.

더미데이터에서는 동일한 배송 시나리오에 대해

* 현장 가이드 없음
* 현장 가이드 제공

을 비교한다.

단, 결과는 실제 카카오 T 퀵의 효율 개선율이 아니라 **설정한 시뮬레이션 조건에서 나타난 결과**로만 표현한다.

## 보조 KPI

* 출입구 탐색시간
* 정차·하역 위치 탐색시간
* 배송지 인근 반복 이동 거리
* 경로 이탈 횟수
* 수령인 연락 횟수
* 배송 완료시간 예측 오차
* 위치·출입 문제로 인한 배송 실패율
* 가이드 확인율
* 가이드 도움됨 비율
* 장소 정보 재검증률

# 14. 기대효과

## 운송인

처음 방문하는 배송지에서도 이전 운송인의 경험을 활용해 출입구·주차·출입 절차 등을 미리 파악할 수 있다.

이를 통해 배송지 도착 이후 발생하는 탐색과 시행착오를 줄일 수 있다.

## 기업

기존 GPS 데이터에 운송인의 현장 맥락을 결합할 수 있다.

기존에는

> 기사가 어디로 이동했는가

를 알았다면,

MileZero를 통해

> 어떤 조건에서 왜 그렇게 이동했고, 다음 배송에서는 어떻게 행동해야 하는가

까지 데이터화할 수 있다.

즉, 단순한 **위치 데이터**를 **장소별 배송 운영 지식**으로 확장한다.

---

# 15. 장기적 활용

장기적으로 MileZero는 장소별로 다음과 같은 운영 지식을 축적한다.

* 차량 진입 가능 영역
* 권장 접근 지점
* 실제 차량 출입구
* 정차·하역 위치
* 차량별 진입 제한
* 시간대별 출입 조건
* 사람 개입 필요 지점
* 건물 내부 이동 규칙

이는 향후 자율주행 배송차량이나 배송로봇이 주소 좌표에 단순히 도착하는 것을 넘어,

**“이 장소에서 실제 배송을 완료하려면 어떻게 행동해야 하는가”**

를 판단하기 위한 Last-50-Feet 운영 지식으로 활용할 수 있다.

# 16. 한계 및 개선점

## 운송인 참여

운송인에게 지속적으로 정보를 작성하도록 요구하는 방식은 현실성이 낮다.

따라서

**자동 감지 → 한 번의 선택 → 필요한 경우만 추가 입력**

순서로 설계하여 운송인의 입력을 최소화한다.

## 정보 최신성

건물 구조, 출입 정책, 공사 상황 등은 변경될 수 있다.

복수 운송인의 반복 확인과 최근 확인일을 중심으로 정보 신뢰도를 지속적으로 갱신한다.

## 개인정보·보안

공동현관 비밀번호, 수령인 연락처, 개인 주소 설명 등은 장소 운영 지식으로 저장하지 않는다.

AI 구조화 과정에서 개인정보와 일회성 배송 정보를 필터링하고, 반복 배송에도 활용 가능한 장소 정보만 저장한다.
