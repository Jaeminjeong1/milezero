# MileZero 기사 역할별 워크플로우 설계

## 목적

심사위원이 MileZero의 지식 순환을 `등록하는 기사`와 `도움 받는 기사` 두 역할로 즉시 구분해 체험하도록 기존 웹앱을 재구성한다. 등록하는 기사는 배송 마찰을 겪은 뒤 짧은 선택형 질문과 선택적 멀티모달 설명으로 경험을 남긴다. 도움 받는 기사는 배송 전에 기존 지식을 안내받고 배송 완료 후 사실성과 유용성을 각각 평가한다.

## 제품 원칙

- 두 역할 모두 상단에서 `마지막 구간은 현장 경험이 안내할게요.`라는 공통 가치를 확인한다.
- 등록 질문은 기사의 책임을 묻지 않고 배송지 환경 때문에 발생한 불편만 확인한다.
- GPS 원본 좌표는 서버로 보내거나 저장하지 않고 브라우저에서 계산한 집계 특징만 사용한다.
- 텍스트·음성·사진은 추가 설명이 필요할 때만 받는다. 선택형 답변만으로도 제보할 수 있다.
- 개인정보가 발견되면 재질문하지 않고 해당 부분만 제거해 저장한다.
- 단일 부정 응답으로 지식을 자동 덮어쓰지 않는다. 독립 기사들의 충분한 변경 신호가 쌓이면 기존 지식 노출을 중단하고 새 후보를 재검증한다.

## 상단 역할 전환

기존 `오늘 배송`과 `다음 배송` 탭을 다음 두 역할 탭으로 바꾼다.

- `등록하는 기사`: 배송 진행, 마찰 감지, 배송 완료 질문, 제보, 즉시 포인트 흐름
- `도움 받는 기사`: 출발 전 안내, 배송 완료, 사실 확인, 유용성 확인, 지식 갱신 흐름

두 탭 모두 공통 `RoleHero`를 표시한다.

```text
마지막 구간은
현장 경험이 안내할게요.
```

공통 제목 아래 보조 문구는 역할에 맞게 달라진다.

- 등록 역할: `불편이 감지되면 배송 완료 뒤 잠깐만 물어볼게요.`
- 도움 역할: `출발 전과 배송지 근처에서 검증된 정보만 먼저 알려드려요.`

## 등록하는 기사 워크플로우

### 1. 배송 진행

현재 배송 카드에 장소, 차량 유형, 배송 상태를 표시한다. `등록하는 기사 · 기사 A` 역할 표식을 함께 보여준다.

### 2. GPS 기반 배송 마찰 감지

브라우저에서 원본 GPS를 다음 집계 특징으로 변환해 `/v1/questions`에 전달한다.

- 배송지 인근 체류시간
- 반복 정차 횟수
- 이동 거리와 실제 변위의 차이
- 유효 표본 수

해커톤 데모에서는 `정지 3회`, `체류 7분`, `짧은 반복 이동`을 자동 재생한다. 화면에는 `평균보다 4분 더 걸렸어요`처럼 결과를 이해할 수 있는 상태를 표시한다.

### 3. 배송 완료 후 질문

배송 중에는 질문하지 않는다. 데모 상태가 `배송 완료`로 전환된 후에만 서버가 생성한 질문 시트를 연다. 질문 시트에는 `기사님의 잘못을 묻는 것이 아니에요`라는 보호 문구를 유지한다.

### 4. 1~2개 선택형 질문과 선택적 설명

질문 API 계약을 단일 질문에서 질문 배열로 확장한다.

```ts
type QuestionItem = {
  id: string;
  question: string;
  choices: string[]; // 정확히 4개 또는 5개
};

type QuestionPlan = {
  shouldAsk: boolean;
  category: FrictionCategory;
  questions: [QuestionItem] | [QuestionItem, QuestionItem];
};
```

- Gemini가 배송 마찰 문맥에 따라 1개 또는 2개의 질문을 생성한다.
- 각 질문은 4~5개의 상호 배타적 선택지를 제공한다.
- 첫 질문에는 항상 `불편하지 않았어요`와 같은 중립 종료 선택지가 포함된다.
- 중립 종료를 고르면 후속 질문과 제보 저장 없이 흐름을 종료한다.
- 문제가 있었다면 질문을 순서대로 한 번에 하나씩 보여준다.
- 모든 선택형 질문이 끝난 뒤 `텍스트`, `음성`, `사진`을 선택적으로 추가한다.
- 선택형 답변만으로 제보할 수 있으므로 추가 설명 입력은 필수가 아니다.

제보 API는 선택 결과를 배열로 받는다.

```ts
type ReportContribution = {
  answers: Array<{ questionId: string; choice: string }>;
  text?: string;
  media?: MediaInput;
};
```

Gemini 분석에는 질문 문장과 선택 결과, 개인정보가 제거된 텍스트, 일시적인 미디어 입력을 함께 전달한다. 원본 미디어는 분석 이후 저장하지 않는다.

### 5. 즉시 보상

제보가 저장되면 기존 정책대로 10P를 즉시 지급한다. 이후 독립 검증과 도움 피드백으로 추가 포인트를 지급한다.

## 도움 받는 기사 워크플로우

### 1. 출발 전 또는 배송지 접근 시 안내

`도움 받는 기사 · 기사 B`가 탭을 열면 `/v1/knowledge`에서 해당 장소와 차량 유형에 맞는 지식을 불러온다.

- `VERIFIED` 지식은 검증된 현장 가이드로 즉시 표시한다.
- `CANDIDATE` 지식은 기본 안내로 사용하지 않는다.
- 데모에서는 기존 검증 지식을 준비해 도움 받는 흐름이 제보자 흐름에 종속되지 않게 한다.
- 안내 카드에는 권장 행동, 차량 조건, 신뢰도와 최근 확인 시점을 표시한다.

### 2. 배송 완료 후 사실성과 유용성 확인

안내 카드의 `배송 완료했어요` 버튼을 누르면 두 질문을 순차 표시한다.

1. `안내받은 정보가 실제 현장과 같았나요?`
   - `맞았어요`
   - `정보가 달랐어요`
2. `이 안내가 배송에 도움이 됐나요?`
   - `도움됐어요`
   - `도움은 없었어요`

피드백 계약은 사실성과 유용성을 분리한다.

```ts
type FeedbackType =
  | "CONFIRM"
  | "CONTRADICT"
  | "HELPFUL"
  | "NOT_HELPFUL";
```

같은 기사는 하나의 주장에 사실 피드백 한 건과 유용성 피드백 한 건을 각각 남길 수 있다. 동일 차원의 재전송은 멱등 처리한다.

### 3. 충돌 처리와 지식 교체

사실과 다르다는 `CONTRADICT`가 서로 다른 기사 2명 이상에게서 쌓이면 기존 기준과 동일하게 주장을 `CONFLICT`로 변경한다.

```text
VERIFIED 지식
  → 독립 CONTRADICT 1건: 신뢰도 하락, 안내 유지
  → 독립 CONTRADICT 2건: CONFLICT, 안내 노출 중단
  → 변경 설명을 새 CANDIDATE로 구조화
  → 독립 CONFIRM 후 VERIFIED
  → 기존 지식을 새 지식으로 교체
```

`NOT_HELPFUL`만으로 사실인 지식을 폐기하지 않는다. 유용성 점수와 정렬 우선순위만 낮춘다. `CONTRADICT`와 `NOT_HELPFUL`이 함께 들어오면 사실 충돌 신호와 낮은 유용성 신호를 각각 저장한다.

충돌을 선택한 기사에게는 필요할 때만 수정 내용을 짧은 텍스트·음성·사진으로 추가할 수 있게 한다. 이 응답도 기존 개인정보 제거 및 멀티모달 분석 파이프라인을 거쳐 새 후보 지식이 된다.

## 백엔드 계약 변경

### 질문 생성

- `QuestionPlanSchema`를 1~2개 `QuestionItem` 배열로 변경한다.
- 각 `choices`는 최소 4개, 최대 5개로 제한한다.
- Gemini JSON schema와 프롬프트에 기사 책임 추궁 금지, 배송지 환경 중심, 중립 종료 선택지 규칙을 포함한다.
- Gemini 실패 시 fallback도 문맥별 1~2개 질문과 4개 선택지를 반환한다.
- 데모 gateway는 결정적인 2개 질문을 반환한다.

### 제보 분석

- `/v1/reports`의 `answerChoice`를 `answers` 배열로 교체한다.
- 배열 길이는 1~2개이며 질문 ID와 선택 문장을 함께 검증한다.
- Gemini 지식 분석 입력에는 선택 결과를 사람이 읽을 수 있는 문맥으로 전달한다.
- 추가 텍스트와 미디어가 없어도 `answers`가 있으면 유효한 제보로 처리한다.

### 피드백과 저장

- `NOT_HELPFUL`을 도메인 타입, Zod schema, API, 인메모리 저장소, Supabase enum에 추가한다.
- 증거 중복 기준을 `FACT(CONFIRM/CONTRADICT)`와 `UTILITY(HELPFUL/NOT_HELPFUL)` 두 차원으로 분리한다.
- 주장에는 `helpfulCount`, `notHelpfulCount`, `utilityScore`를 저장한다. `utilityScore`는 `0.5 + HELPFUL×0.1 - NOT_HELPFUL×0.15`를 0~1 범위로 제한해 계산한다.
- `evaluateClaim`은 사실 피드백으로 상태를 결정하고, 유용성 피드백으로 두 카운트와 정렬용 `utilityScore`를 계산한다.
- `CONFLICT` 지식은 `/v1/knowledge`의 안내 목록에서 제외한다.

## 프런트엔드 상태

등록 흐름은 다음 상태를 사용한다.

```text
delivering
→ friction_detected
→ delivered
→ asking(1/2)
→ optional_detail
→ submitting
→ rewarded
```

도움 흐름은 다음 상태를 사용한다.

```text
loading_guide
→ guide_ready
→ delivered
→ fact_feedback
→ utility_feedback
→ feedback_complete
```

등록 흐름의 상태와 도움 흐름의 상태를 분리해 한 역할의 오류나 재실행이 다른 역할을 초기화하지 않게 한다.

## 오류와 안전 처리

- 질문 생성 실패 시 책임 중립적인 fallback 질문을 보여준다.
- 지식 조회 실패 시 기존 카드 대신 재시도 가능한 오류 상태를 보여준다.
- 사실 피드백은 성공했지만 유용성 피드백이 실패한 경우 사실 피드백을 되돌리지 않고 두 번째 요청만 재시도한다.
- 중복 피드백은 기존 결과를 반환하고 통계와 포인트를 중복 반영하지 않는다.
- 개인정보 제거, 미디어 8MB 제한, MIME 검증, 원본 미디어 비저장 원칙을 유지한다.

## 테스트 기준

### 백엔드

- 질문 schema가 질문 1~2개와 선택지 4~5개만 허용한다.
- fallback과 데모 Gemini가 기사 책임을 묻지 않는 유효한 질문 배열을 반환한다.
- 선택형 답변만으로 제보가 저장되고 10P가 지급된다.
- 동일 기사가 사실·유용성 피드백을 각각 한 건 남길 수 있다.
- 독립 `CONTRADICT` 2건에서 `CONFLICT`가 되고 안내 목록에서 제외된다.
- `NOT_HELPFUL`만으로는 사실 상태가 바뀌지 않는다.

### 프런트엔드

- 최상단에 `등록하는 기사`와 `도움 받는 기사` 탭이 표시된다.
- 두 탭 모두 공통 가치 문구를 표시한다.
- 배송 완료 전에 질문이 열리지 않는다.
- 1~2개 질문을 순차 진행하고 선택형 답변만으로 제보할 수 있다.
- 도움 탭에서 안내를 먼저 보고 배송 완료 후 사실성과 유용성을 순서대로 평가한다.
- 부정 피드백 후 기존 안내의 신뢰도 하락 또는 노출 중단 상태를 명확히 보여준다.

### 통합 검증

- 전체 테스트, 타입 검사, 빌드와 데모 QA를 통과한다.
- 390px 모바일과 1280px 데스크톱에서 두 역할 흐름을 브라우저로 완주한다.
- 콘솔 오류, 가로 오버플로와 키보드 접근 문제를 확인한다.
- 프로덕션 Fastify 서버에서 SPA, `/ready`, API 404를 smoke test한다.

## 완료 기준

- 심사위원이 상단 탭만 보고 두 기사 역할을 구분할 수 있다.
- 등록 역할에서 GPS 마찰 감지부터 질문, 선택적 설명, 즉시 포인트까지 완주할 수 있다.
- 도움 역할에서 사전 안내부터 배송 완료 후 사실·유용성 피드백까지 완주할 수 있다.
- 독립 변경 신호 2건 이후 기존 지식이 더 이상 안내되지 않고 새 후보 검증 경로로 전환된다.
- 개인정보를 재질문하거나 원본 GPS·미디어를 영구 저장하지 않는다.
